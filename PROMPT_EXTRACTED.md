1. Princípios Fundamentais Universais

Antes de mergulhar em cada tipo de visualização, existem princípios que se aplicam a todos eles:

Princípio

Aplicação Prática

Clareza sobre complexidade

Cada elemento deve ter um propósito claro. Evite decoração sem função.

Hierarquia visual

Use tamanho, cor e posição para guiar o olhar. O mais importante deve ser o mais proeminente.

Simplicidade

“Quando tudo é enfatizado, nada se destaca.” Remova o redundante.

Consistência

Mesmas cores, fontes e estilos para elementos similares em todo o documento.

Espaço em branco

Respire. Margens e espaçamento evitam blocos densos de texto ou formas.

Acessibilidade

Contraste adequado, fontes legíveis, não dependa apenas de cores para transmitir significado.

Foco em uma ideia central

Um infográfico, mapa ou diagrama deve comunicar uma ideia principal.

2. Mapas Mentais

Metodologia (Técnica de Tony Buzan)

Tema central no meio — uma palavra/frase central, em letras grandes, com uma imagem ou ícone.

Ramos principais — divergem do centro como galhos de árvore. Cada ramo = um subtópico principal.

Sub-ramos — detalham cada ramo principal. Use palavras-chave (não frases longas).

Cores por categoria — cada ramo principal tem uma cor distinta. Isso agrupa visualmente as informações.

Imagens e símbolos — o cérebro retém imagens melhor que palavras. Adicione ícones simples.

Conexões — linhas curvas (não retas) conectam os nós, reforçando a associação.

Design Otimizado

Aspecto

Recomendação

Fonte

1 ou 2 fontes no máximo. Tamanho decrescente: central > ramos > sub-ramos.

Cores

Paleta de 4-6 cores. Uma por ramo principal + neutros. Evite cores neon.

Layout

Radial, com o centro no meio. Deixe espaço entre ramos para não “sujar” visualmente.

Texto

Palavras-chave de 1-3 palavras. Evite frases completas.

Ferramentas Recomendadas

MindMeister — colaborativo, templates, modo apresentação.

FigJam (Figma) — ideal para equipes de design/produto, com recursos de IA.

Excalidraw — estética handmade, leve, gratuito, integra com Mermaid.

XMind — robusto, com modos de estrutura (lógico, árvore, timeline).

3. Organogramas

Estrutura e Tipos

Hierárquico tradicional — pirâmide, ideal para estruturas rígidas.

Horizontal/Flat — mostra equipes lado a lado, bom para startups.

Matricial — mostra reporte duplo (funcional + por projeto).

Por função — agrupa por departamentos (TI, Marketing, RH).

Boas Práticas de Design

Níveis por cores — cada nível hierárquico (C-level, gerentes, analistas) com uma cor ou tonalidade diferente.

Linhas claras — use conectores diretos e consistentes. Evite linhas cruzadas.

Caixas uniformes — mesmo tamanho para cargos do mesmo nível.

Informação essencial apenas — nome do cargo (e opcionalmente nome da pessoa). Evite descrições longas.

Layout limpo — alinhamento rigoroso, espaçamento consistente entre caixas.

Ferramentas Recomendadas

Draw.io (diagrams.net) — gratuito, offline, exporta SVG/PDF, tem templates de organograma.

Lucidchart — importa dados de planilhas para gerar organogramas automaticamente.

Canva — templates bonitos e prontos para apresentações.

7. Aplicação por Contexto

Para Aulas/Educação

Use mapas mentais para introduzir conceitos e conectar ideias.

Infográficos comparativos para contrastar teorias ou métodos.

Timelines para histórico/evolução de conceitos.

Processos (flowcharts) para explicar algoritmos ou metodologias.

Dica: aposte na qualidade sobre quantidade. Um infográfico interativo vale mais que 10 slides estáticos.

Para Relatórios

Infográficos estatísticos com dados-chave ampliados.

Gráficos de tendência (linha/barras) para evolução temporal.

Mantenha fontes citadas — credibilidade é visível.

Design para print E digital desde o início.

Para Documentação de Apps

Use o Modelo C4 para estruturar a documentação visual.

Mermaid.js para todos os diagramas em markdown (README, Wikis).

Excalidraw para sketches de arquitetura e brainstorming.

Mantenha nomes consistentes: se chama “User Service” no diagrama, chame assim no texto.

Docs-as-Code: mantenha diagramas junto ao código, versionados no Git.

8. Checklist Final de Qualidade

Antes de publicar qualquer visualização, verifique:

☐ Uma ideia central — consigo resumir em uma frase?

☐ Hierarquia clara — o olhar é guiado naturalmente do mais ao menos importante?

☐ Texto mínimo — cortei tudo que não é essencial?

☐ Cores consistentes — uso a mesma paleta em todo o documento?

☐ Contraste adequado — legível em mobile e dark mode?

☐ Fontes limitadas — no máximo 2 fontes?

☐ Espaço em branco — há respiro entre elementos?

☐ Fontes citadas (infográficos/relatórios) — dados são verificáveis?

☐ Formato adequado — exportei no formato certo para o meio (PNG para web, PDF para print, SVG para escalabilidade)?

☐ Teste de compreensão — alguém de fora entendeu em 10 segundos?

Regras de Layout Automático

Mapas mentais: Máximo 6 ramos principais. Se ultrapassar, sugerir divisão em múltiplos mapas.

Organogramas: Máximo 3 níveis visíveis por página. Paginação automática se necessário.

Infográficos: Regra dos 3 níveis (must/should/can see). Densidade máxima de 60% da área.

Arquitetura: Máximo 20 elementos por diagrama C2. Se ultrapassar, sugerir C1 + múltiplos C2.

Grafos: Layout force-directed com repulsão ajustável. Labels só aparecem se houver espaço.

Tipografia

Fontes padrão: ‘Inter’ (headings), ‘Source Sans Pro’ (body) — fallback para system fonts

Tamanhos escalonados: 32px (título), 24px (subtítulo), 16px (body), 12px (caption)

3.7 Segurança e Compliance

Camada

Implementação

Path Traversal

Todas as paths são resolvidas com path.resolve() e verificadas contra path.startsWith(OUTPUT_DIR). Rejeita se false.

Sanitização

Nomes de arquivo whitelist: /^[a-z0-9_-]+\.(mmd|json|svg|png)$/i. Rejeita caracteres especiais.

CORS

Frontend e Backend rodam em localhost. CORS restrito a http://localhost:*. Nenhuma origem externa permitida.

Input Validation

Zod schemas rigorosos em TODAS as tools. Max length em strings, max items em arrays, enum em tipos.

Rate Limiting

Max 10 requisições/minuto por sessão MCP (in-memory counter).

Sandbox

Backend não executa shell arbitrário. Apenas mmdc via spawn controlado. Sem eval(), sem new Function().

📎 ANEXO A — Decisões de Arquitetura (ADRs)

ADR-001: Por que SSE em vez de WebSocket?

Contexto: Precisamos de comunicação real-time Backend↔Frontend.

Decisão: Usar Server-Sent Events (SSE).

Justificativa: SSE é unidirecional (servidor → cliente), que é exatamente o que precisamos. Mais simples que WebSocket (sem handshake complexo), funciona sobre HTTP, tem reconexão automática no browser. WebSocket seria overkill.

Consequências: Não suporta comunicação cliente → servidor via SSE. Para comandos do Frontend para o Backend, usarei HTTP POST simples.

ADR-002: Por que Alpine.js em vez de React/Vue/Svelte?

Contexto: Restrição de PC fraco; bundle deve ser mínimo.

Decisão: Alpine.js.

Justificativa: ~15KB vs ~40KB (React+ReactDOM) ou ~30KB (Vue). Sem Virtual DOM = menos CPU. Sintaxe declarativa no HTML = menos JS para parsear. Ideal para dashboards interativos leves.

Consequências: Ecossistema menor (menos libs prontas). Componentização é via x-data e templates, não single-file components.

ADR-003: Por que Mermaid.js como formato intermediário?

Contexto: Precisamos de um formato que IA gere facilmente e que seja versionável.

Decisão: Mermaid.js (texto/Markdown) como lingua franca.

Justificativa: É texto puro (git-friendly), amplamente suportado (GitHub, Notion, Obsidian), a IA já conhece a sintaxe, e renderiza para SVG/PNG. Alternativas (D2, PlantUML) têm menor adoção.

Consequências: Customização visual é limitada (themeVariables). Mitigamos com post-processing SVG (CAMADA 3).

ADR-004: Por que Backend pré-renderiza SVG?

Contexto: PC fraco pode ter dificuldade em renderizar Mermaid no browser.

Decisão: Backend gera .svg de cache junto com .mmd.

Justificativa: O Frontend pode mostrar o SVG instantaneamente enquanto aplica o tema. Se o usuário quiser tema custom, o Frontend re-renderiza. Melhor UX para o caso comum (tema default).

Consequências: Backend precisa de mermaid-cli instalado. Uso de disco aumenta (~2x arquivos).

Fim da Arquitetura Revisada. Este documento elimina os gaps identificados na revisão crítica e estabelece uma base robusta para implementação. Não prossiga sem aprovação do Spike #0. ```
